# Gateway 生命周期单一恢复者收敛技术方案

## 一、背景与问题陈述

### 1.1 现象

在 Default(18809) managed profile 场景下持续出现以下交错症状：

- App 提示「初始化失败」「运行异常」「disconnected (1006): no reason」
- `/readyz` 与 `/healthz` 短时间内反复在 `200` 与 `connection refused` 之间切换
- Supervisor 日志里在数分钟内重复出现：
  - `pseudo-live auto-restart scheduled profile=default port=18809`
  - `restartProfile coalesced existing-task ...`
  - `startProfile launched ... port=18809`
- Gateway 自身日志显示进程已经 `ready`，但 App 仍触发 recovery
- 同一时间段，App bootstrap 日志频繁打印 `recovery skipped start; profile is observe-only`，但其实当前关注 profile 是 managed 的 default

### 1.2 根因分类

问题已经不是单点 bug，而是控制平面复杂度本身导致的稳定性塌陷，核心可拆为两类：

1. **多方并行恢复（控制平面竞态）**
   - App `AppBootstrapCoordinator` 会基于 runtime snapshot 触发 restart
   - Supervisor 内部有：
     - `scheduleManagedUnresponsiveRestartIfNeeded`
     - `maybeSchedulePseudoLiveRecovery`
     - `handleProcessTermination` 自动重启
     - 安装/升级期间的 upgrade handoff
   - 三层叠加导致：当 Gateway 进入 unresponsive 时，多个触发点同时下发 restart，配合 coalescing 也只能合并到「一次又一次」，无法避免拉锯

2. **OpenClaw Gateway 内部进入伪存活（数据平面 Hang）**
   - 进程仍占有 18809 端口
   - Node/V8 事件循环持续在 `PromiseFulfillReactionJob`、`MicrotaskQueue::RunMicrotasks`、`Heap::CollectGarbage`
   - 表现：`/readyz` 不响应、WebSocket 1006、HTTP 超时
   - 这层根因不在 Swift 层，必须由 OpenClaw 模块级修复才能根治

### 1.3 与「自己安装的 OpenClaw（LaunchAgent）」对比

| 维度 | OpenClaw 自带 LaunchAgent | EZRWorker 托管模式 |
| --- | --- | --- |
| 控制平面层数 | 单层守护 | App + Supervisor + Gateway 三层 |
| 恢复决策 | 单一来源（launchd KeepAlive） | App、Supervisor 多触发点 |
| 健康判定 | 进程是否存活 | TCP listening + `/readyz` + 状态机 |
| Profile/多实例 | 单实例 | 多 profile + adopt/legacy/external |
| 升级路径 | 重新安装 plist | App 安装 + supervisor 替换 + Gateway 移交 |
| 失败放大效应 | 低 | 高（任意一层判错即触发重启风暴） |

结论：稳定性差异不是「谁的代码烂」，而是托管模式天然把控制面复杂度提升了一个数量级，必须用更严格的职责边界与可证据驱动的修复闭环。

## 二、目标

1. **唯一恢复者**：所有 Gateway lifecycle 恢复决策（start / restart / stop）集中在 Supervisor，App 端不再触发任何 lifecycle 操作。
2. **可证据根因定位**：每次出现 pseudo-live 必须自动产出 sample 栈与上下文，使 OpenClaw 卡点可被定位到模块级。
3. **收敛而非加策略**：本方案不引入新的兜底重试，只删减重复恢复入口；新增动作只发生在「证据采集」与「日志分类」。
4. **不影响其它运行形态**：legacy reuse、external reuse、observe-only、Debug Run 行为不回归。

## 三、当前状态盘点（截至 2026-05-09）

已落地的相关改动：

- App 端
  - `AppBootstrapCoordinator` 对 `.unresponsive`/`.failed` managed runtime 走 `runtimeShouldDeferLifecycleToSupervisor`，所有日志带 `slug` 与 `port`
  - 全仓审计 `supervisorClient.restartProfile` 与 `processManager.restart()` 调用点：仅出现在用户显式动作链路（Profile actions 重启按钮、配置变更后必须重启、LaunchAgent 交接后重启）
  - `HomeDashboardView` 在 `.unresponsive` 状态下禁用「重启」按钮并改文案为「Supervisor 自动恢复中」，避免连点叠加
- Supervisor 端
  - 新增 `SupervisorController+Recovery.swift`，统一入口 `requestLifecycleRecovery(reason:operation:)`
  - 4 个恢复触发源全部接入：
    - `unresponsive`：`scheduleManagedUnresponsiveRestartIfNeeded`
    - `terminationRelaunch`：`handleProcessTermination` ready/alive relaunch 分支
    - `terminationAdoptStartup`：`handleProcessTermination` adopt-startup 分支
    - `terminationLauncherExited`：`handleProcessTermination` launcher-exit 分支
    - `terminationHandoff`：`handleProcessTermination` upgrade handoff 分支
  - 统一冷却（`pseudoLiveAutoRestartCooldown`）+ post-restart settle 窗口 + handoff 节流（`recordRestartHandoff`）
  - 统一日志前缀 `lifecycle recovery decided/skipped/throttled/dropped reason=...`
  - `restartProfile` 保留 in-flight task 合并，行为不变
  - `waitForGatewayReady` launcher-exit 延迟失败 / 接管不变
- Pseudo-live 证据闭环
  - 自动 `/usr/bin/sample` 抓栈，落盘 `~/Library/Application Support/EZRWorker/diagnostics/pseudo-live-samples/sample-{slug}-{port}-{pid}-{timestamp}.txt`，180s 冷却
  - 同名同目录 `*.meta.json`：`profileSlug/port/pid/ownership/adoptionKind/healthState/readyState/lastReadyAt/unhealthySince/lastUnhealthyReason/lastLifecycleMessage/...`
  - 抓栈成功/失败均落 lifecycle 日志（`pseudo-live sample capture done|failed`）
- Gateway 端
  - `OPENCLAW_SKIP_CHANNELS=1` 注入，避免 channel 启动拖累首轮就绪
  - `update.checkOnStart=false`、`update.auto.enabled=false`

未解决：

- 回归矩阵未系统执行（Phase 5）：managed/legacy/observe-only/adopted/upgrade handoff 7 场景需逐一过一遍
- pseudo-live 根因（OpenClaw 内部）尚无栈级结论，等待 ≥ 3 份 meta+sample 后聚类

## 四、设计方案

### 4.1 控制平面边界（核心）

```
┌────────────────────┐        XPC 状态订阅          ┌──────────────────────┐
│   EZRWorker App    │  ─────────────────────────▶  │  EZRWorkerSupervisor │
│  （UI 与状态消费）  │  ◀─────────────────────────  │  （唯一 lifecycle 恢复者）│
└────────────────────┘        SnapshotStream         └──────────────────────┘
        │                                                   │
        │  仅在用户显式动作（启动/停止/重启）下发指令         │
        ▼                                                   ▼
   start / stop / restart  ──────────────────────▶   GatewayProcess
```

约束：

- App 仅在「用户显式点击 / autoStart 首次拉起」时下发 start
- App 永远不会基于 runtime 状态自行下发 restart
- Supervisor 内所有 lifecycle 触发点（unresponsive、pseudo-live、launcher-exit、handoff）统一汇总到一个调度器，遵循同一节流与 coalescing 规则

### 4.2 App 端单恢复者改造

变更点（在已有 defer-to-supervisor 基础上继续清零）：

1. `AppBootstrapCoordinator`
   - 移除 `.unresponsive` 与 `.failed` 分支里仍保留的 `restartProfile` 调用，仅保留首次 `startProfile`
   - `recovery skipped` 系列日志补 `slug=` 与 `port=`，避免误读 observe-only / managed 关系
2. `GatewayProcessManager` / `SupervisorClient` 调用面
   - 标注哪些路径属于「用户显式动作」，剩余路径不允许调用 restart
3. UI 层
   - 当 runtime 处于 `.unresponsive` 时，UI 提示「Supervisor 正在自动恢复」，禁用「重启」按钮短时间（避免用户连点叠加）

落地原则：保留 observe-only 与 legacy 的现有恢复路径不变，只对 managed/supervised 收口。

### 4.3 Supervisor 端恢复触发点收口

将以下入口统一接入一个 `LifecycleRecoveryCoordinator`（命名见实现章节）：

- `scheduleManagedUnresponsiveRestartIfNeeded`
- `maybeSchedulePseudoLiveRecovery`
- `handleProcessTermination` 内的 self-restart
- upgrade handoff 完成后的 resume start

统一规则：

| 规则 | 当前 | 收口后 |
| --- | --- | --- |
| 节流 | 每个触发点各自节流 | 单一窗口 + 单一冷却 |
| 合并 | inFlightRestartTasks per profile | 不变 |
| 决策日志 | 散落在多个文件 | 统一 `lifecycle recovery decided reason=...` |
| 证据抓取 | 仅 pseudo-live | 所有 unresponsive 触发点共享 sample 抓取冷却 |

### 4.4 Pseudo-live 证据闭环

在已有自动 sample 落盘基础上：

1. 每份 sample 同时落一个 `meta.json`：
   - `profileSlug`、`port`、`pid`、`ownership`、`adoptionKind`
   - `lastReadyAt`、`unhealthySince`、`healthState`
   - 最近 N 条 lifecycle 日志快照
2. 每次抓栈写一条 lifecycle 日志：
   - `pseudo-live sample capture done ... file=...`
3. 收集 ≥ 3 份后人工/脚本聚类，输出「热点函数 → OpenClaw 模块」映射，进入 OpenClaw 根因修复阶段（不在本方案 Swift 侧）。

### 4.5 状态唯一真相源

- `SupervisorRecord` 为 Gateway lifecycle 唯一权威状态来源
- App 仅消费 `SupervisorProfileRuntime` snapshot 字段，不再二次推断（如「是否需要重启」）
- snapshot 字段最小可见集需保证 UI 展示足够，但**不允许** App 据此做 lifecycle 决策

### Phase 4 — 回归矩阵（半天）

覆盖以下场景，要求观察 lifecycle 日志，不要求重启风暴消失（取决于 Phase 5 OpenClaw 修复），但要求触发点单一、可定位：

| 场景 | 期望 |
| --- | --- |
| 全新登录后首次启动 default | 仅一次 `startProfile begin`，无 App 端 restart |
| Default 进入 pseudo-live | Supervisor 触发 `lifecycle recovery decided reason=pseudo-live`，App 仅记录 `recovery deferred` |
| Legacy 18789 observe-only | App 不触发任何 start/restart |
| External adopted | 同上 |
| Supervisor 升级（pkg 重装）| 触发 upgrade handoff，App 不重复发 start |
| 用户手动「停止」 | `userStoppedAt` 持久化，autoStart 不复活 |
| 用户手动「重启」 | App 显式发 restart，触发 `restartProfile requested ... reason=user` |

### Phase 5 — OpenClaw 根因修复（独立排期）

- 输入：≥ 3 份 pseudo-live sample + meta + lifecycle 日志
- 输出：OpenClaw 模块级修复（如 microtask 风暴的具体插件 / 任务循环）
- 不在本方案 Swift 侧落地，单独立 plan

## 六、风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| App 单恢复者改造误删用户路径 | 用户点重启无效 | 在删除前用 grep + 调用栈审计，保留显式动作路径 |
| Supervisor 协调器引入 bug | 所有恢复失效 | Phase 2 灰度：先把 4 个入口的日志统一，再切真实调度 |
| Pseudo-live 抓栈占盘 | 长期累积磁盘占用 | 文件名带时间戳 + 180s 冷却 + 后续加保留策略（仅保留最近 N 份） |
| Observe-only / legacy 行为回归 | 老用户既有流程被破坏 | 收口仅作用于 `sourceKind == .managed && managementMode == .managedByEZRWorker` |
| 升级 handoff 受影响 | 升级时 Gateway 错失重启 | Phase 2 协调器内对 upgrade handoff 单独路径白名单 |

回滚策略：

- 每个 Phase 一个独立提交
- Phase 2 协调器以特性开关 `EZRWORKER_LIFECYCLE_COORDINATOR=1` 默认开，紧急时关闭回退到旧多入口

### 8.3 已收集的关键事实（不重复诊断）

- pseudo-live 时 `sample` 抓到的热点：`Builtins_PromiseFulfillReactionJob` / `MicrotaskQueue::RunMicrotasks` / `Heap::CollectGarbage`
- gateway 自身日志显示 `ready` 后才被 supervisor 标 unresponsive，意味着是「ready 之后某段时间被业务任务卡住」，而不是启动期问题
- 18809 端口在 unresponsive 期间持续 LISTEN，但 `/readyz` 不返回 → 经典 event loop 阻塞
- 与 legacy 18789 自带 LaunchAgent 共存时，legacy 永远不进入此状态，进一步佐证根因在 managed 模式下 App/Supervisor/Gateway 三方交互而非 OpenClaw 单进程运行本身

## 九、修订（2026-05-09）：unresponsive 判定过敏导致重启风暴

### 9.1 现象（在 shop 18809 上重现）

- `shop` profile 已成功 `ready`，端口 18809 持续 LISTEN
- 大约 ready 后 60s+，supervisor 触发 `lifecycle recovery decided reason=unresponsive op=restart`，附带 `pseudo-live sample capture`
- 紧接着 `restartProfile requested -> stopResult ok -> startProfile begin/launched`，gateway 收到 SIGTERM 后再次启动
- 30 分钟后又重复一轮，导致用户感知"反复初始化失败 / 18809 又异常了"

### 9.2 根因复评

- 现行 `gatewayUnresponsiveThreshold = 60s` 对 OpenClaw 当前真实负载偏激进：
  - LLM 调用（含模型 fallback、auth 校验失败回退）容易让 lane task 持续 100s+
  - `document-extract` / `microsoft` / `web-readability` 等插件 `staging bundled runtime deps` 后置安装会让 event loop 长时间繁忙
  - `logs.tail` 命中真实 50s+ 的响应（你日志中存在 50651ms 的 `ws res`）
- 这些都不是真死，但 `/readyz` 在这些窗口里会无响应，导致 60s 阈值误判
- 当前 `recordRestartHandoff` 限频是 60s 内 3 次，对"30 分钟一次"的抖动起不到节流作用

### 9.3 修复方向

1. 放宽 unresponsive 阈值：`gatewayUnresponsiveThreshold` 60s → 240s
2. 收紧自动重启总频率：`pseudoLiveAutoRestartCooldown` 120s → 600s
3. 收紧多轮限频：`gatewayRestartHandoffWindow` 60s → 1800s（30min）；`maxGatewayRestartHandoffsInWindow` 3 → 2
4. **强保护**：在 `requestLifecycleRecovery` 的 `unresponsive` 分支，若 `record.portListeningPID` 仍非 nil（端口仍在 LISTEN）且最近一次已经触发过 handoff，则只抓 sample，不再重启；记日志 `lifecycle recovery skipped reason=unresponsive detail=port-still-listening profile=...`

### 9.4 不做什么

- 不引入新的"健康判定指标"（不打更多 probe，不加业务级 ping）；只调阈值与单一保护分支，保持单一恢复者结构不变
- 不修改 App 端逻辑；这是 supervisor 内部的判定收敛
- 不删除 pseudo-live sample 抓取；样本数据继续累积用于 OpenClaw 根因排期

### 9.5 验收

- 在 `shop`（带 LLM 鉴权失败 + 插件 backfill）的真实场景下 30 分钟内至多触发一次自动重启
- pseudo-live samples 仍照常落盘
- `lifecycle recovery skipped reason=unresponsive detail=port-still-listening` 日志在 LISTEN 但 `/readyz` 慢的窗口内出现至少一次
