# 设置页面重新设计技术方案

## 一、背景与现状

当前主线设置页位于 `EZRWorkerApp/EZRWorker/Views/Settings/AppSettingsView.swift`，整体结构是：

```text
VStack
  PageHeroHeader
  Form(.grouped)
    账户
    Profiles
    Gateway
    OpenClaw 终端
    环境
    关于
```

主要问题：

- 主体使用 `Form(.grouped)`，macOS 默认会产生系统表单的内边距、行宽与分组视觉，实际内容不会像数字员工、定时任务、消息渠道页一样撑满 detail 区域。
- Profile 卡片虽然内部 `.frame(maxWidth: .infinity)`，但仍被 `Form` 的 row/inset 约束包住，视觉上不像满宽页面。
- 设置页内大量说明、Profile 信息、路径、错误提示使用 `.caption`，而其他主线页面常用 `20 / 16 / 15 / 14` pt 的固定字号，导致设置页内容明显小一档。
- 信息层级偏“表单堆叠”，Profile、Gateway、终端、环境这些高频信息没有卡片化聚合，用户扫描成本较高。
- 当前设置页已新增“打开内嵌终端”能力，入口位于 `OpenClaw 终端` Section，需要在重设计中保留并强化为清晰的操作卡片。

对照页面：

- `AgentGridView`：`ScrollView + VStack`，页面横向 padding 28，卡片自绘并撑满网格宽度。
- `CronTaskView`：`ScrollView + VStack + LazyVGrid`，标题 20、正文 16、详情 15。
- `ChannelView`：`ScrollView + LazyVGrid`，卡片标题 20、副标题 15、按钮 16，并主动定义字号常量。
- `SkillsView` / `ModelConfigView` 仍使用 `List`，但设置页内容更复杂，不适合继续依赖系统 `Form`。

## 二、设计目标

1. 设置页内容文字大小与其他主线页面保持一致，正文不再默认使用 `.caption`。
2. 页面主体撑满 detail 区域，横向空间充分利用；概览、操作、系统信息支持多列卡片，Profiles 单独使用横向 carousel。
3. 保留现有功能和业务逻辑，不改 `GatewayProcessManager`、`GatewayProfileStore`、`SupervisorClient`、`AuthSessionStore` 的行为。
4. 降低信息扫描成本，把 Profiles、Gateway、终端、环境、账户、关于拆成清晰卡片。
5. 保持 macOS 原生控件可用性，Toggle、Button、Sheet、ConfirmationDialog、Alert 的交互不降级。
6. 保留新增的内嵌终端入口，并明确展示当前 Profile 与工作目录，避免用户误以为打开的是全局 shell。
7. Profiles 区域减少纵向占用，改为横向滑动浏览，避免 profile 数量增加后把设置页撑得过长。
8. 统一卡片高度和错误呈现，避免同一组卡片出现“有高有矮”的视觉跳动。
9. 收敛重复操作入口，Gateway 进程启停只保留在 Profile 卡片中，Gateway 卡片只承担状态说明。

非目标：

- 不重做 Profile / Supervisor / Gateway 生命周期协议。
- 不改旧 `LegacyCompatibility/Views/SettingsView.swift`。
- 不新增模型配置、渠道配置等新功能入口。
- 不处理深色/浅色之外的新主题系统。
- 不重做内嵌终端本身的执行环境、命令保护和窗口生命周期，只调整设置页入口展示。

## 三、推荐布局

### 3.1 页面外层

将 `Form(.grouped)` 替换为自绘滚动页面：

```swift
ScrollView {
    VStack(alignment: .leading, spacing: 24) {
        heroSection
        statusOverviewGrid
        profilesSectionCard
        operationsGrid
        systemInfoGrid
    }
    .padding(.horizontal, 28)
    .padding(.top, 24)
    .padding(.bottom, 28)
    .frame(maxWidth: .infinity, alignment: .topLeading)
}
.frame(maxWidth: .infinity, maxHeight: .infinity)
.background(Color(nsColor: .windowBackgroundColor))
```

布局原则：

- 外层不设置最大宽度，确保 detail 区域可被内容填满。
- 主体横向 padding 建议用 28，与 `AgentGridView` 对齐；如果希望更紧凑，可用 20，与 `CronTaskView` / `ChannelView` 对齐。
- 所有卡片都使用 `.frame(maxWidth: .infinity, alignment: .leading)`。
- overview、operations、system 信息区使用 `LazyVGrid` 填满横向空间，窄屏自动落为单列；Profiles 列表使用横向 `ScrollView`。

### 3.2 信息架构

推荐页面结构：

```text
设置
Profile、运行环境与版本信息。

[当前 Profile] [WebSocket] [环境]

┌ Profiles ───────────────────────────────────────────────┐
│ 新建 / 导入 / 刷新                                       │
│ 当前：Default。左右滑动查看更多 Profile                  │
│ ← ┌ Profile Card ┐ ┌ Profile Card ┐ ┌ Profile Card ┐ →  │
└──────────────────────────────────────────────────────────┘

┌ OpenClaw 终端 ─────────────┐ ┌ 环境 ──────────────────────┐
│ 当前 Profile / 工作目录     │ │ Node.js / OpenClaw / 重检查 │
│ 打开内嵌终端                │ │ 环境状态                   │
└───────────────────────────┘ └───────────────────────────┘

┌ 账户 ─────────────────────┐ ┌ 关于 ──────────────────────┐
│ 手机号 / 显示名称 / 退出  │ │ 版本 / 构建号              │
└──────────────────────────────────────────────────────────┘
```

建议顺序：

1. `statusOverviewGrid`：当前 Profile、WebSocket、环境状态的轻量摘要，让用户进入设置页先看到关键状态。
2. `profilesSectionCard`：Profile 是当前设置页最重的内容，保留单独满宽区域，但内部用横向滑动 carousel 控制纵向高度。
3. `toolGrid`：OpenClaw 终端与环境信息固定放在同一行双卡片区，双列均分整行，统一作为“工具 / 运行环境”层。
4. `systemInfoGrid`：账户、关于等低频信息放在下一行。

### 3.3 Profiles 横向 Carousel

Profiles 区域不再使用 `Picker + 垂直网格`。切换 Profile 的入口放进每张 Profile 卡片内部，避免和卡片操作重复；profile 数量增加时，列表保持单行横向滚动。

布局规则：

- 外层仍是满宽 `SettingsSectionCard`。
- 工具栏只保留 `新建 Gateway/Profile`、可选的 `导入 ~/.openclaw`、`刷新运行态`。
- 当前上下文用说明行展示：`当前：xxx。左右滑动查看更多 Profile；点击卡片里的“切换到此 Profile”切换上下文。`
- Profile 列表使用 `ScrollView(.horizontal) + LazyHStack`。
- 单张 Profile 卡固定宽度约 `420`，固定高度约 `392`，carousel 高度约 `408`。
- 如果有 5 个 profiles，展示为同一横向队列中的 5 张固定宽度卡片；当前窗口能看到几张取决于宽度，其余通过左右滑动查看，不再变成 `2 + 2 + 1` 的多行网格。

Profile 卡片内容压缩策略：

- 标题行：displayName、`当前`、来源、运行态 badge。
- Toggle：保留 `登录后自动恢复`。
- 核心指标：端口、配置、PID、最近探测，使用 2x2 小指标格。
- 配置状态：managed profile 使用 `已准备 / 未准备`；legacy profile 不要求重新 setup，配置文件存在时展示 `可复用`，缺失时展示 `缺配置`。
- 运行态标签：legacy profile 在未运行但旧配置可用时，展示 `可复用`，不展示通用的 `已停止`，避免把“当前未启动”和“旧配置不可用”混在一起。
- 运行错误：统一放入固定高度的一行状态提示，红色展示并通过 tooltip 保留完整错误，避免有错误的卡片单独变高。
- 路径：只展示 `Config` 与 `Workspace` 两行紧凑路径；路径用 `~` 缩写、单行中间截断；点击路径栏弹出完整路径面板，并在面板里支持选中和复制，避免行内选中后文字撑出容器。
- 操作按钮：保留 `切换到此 Profile`、`准备配置/检查配置`、`启动`、`停止`、`重启`、`删除`，由 profile 类型与当前 runtime 决定展示。

### 3.4 OpenClaw 终端入口

`OpenClaw 终端` 从原来的 Form Section 升级为操作卡片，作为设置页的高级工具入口。

展示内容：

- 当前 Profile：展示 `displayName` 与 `slug`。
- 工作目录：默认展示缩略后的 monospaced 路径；点击路径栏弹出完整路径面板，面板内可选中和复制。
- 主操作：`打开内嵌终端`，图标使用 `terminal`。
- 说明文案：终端会进入当前 profile 环境，可执行 `openclaw configure --section model`、`openclaw agents list` 等命令；`openclaw gateway` 会被保护，避免重复启动 Gateway。

交互规则：

- 有 `selectedProfile` 且有 `selectedResolution` 时，按钮调用现有 `openWindow(id: "profile-terminal", value: selectedProfile.id.uuidString)`。
- 没有可用 Profile 时，卡片展示空态说明并禁用打开操作。
- 切换 Profile 后，卡片内容必须同步更新，打开的终端窗口使用点击当下的 Profile ID。
- 重设计只迁移入口视觉，不修改 `ProfileTerminalView`、`ProfileCLIService` 和窗口注册逻辑。

### 3.5 Gateway 展示收敛

设置页不再保留独立的 `Gateway` 状态卡或控制卡。

原因：

- Gateway 生命周期操作已经统一收敛到 Profile 卡片中，设置页再次展示会形成重复入口。
- 其他主界面已经提供 Gateway 相关状态与恢复信息，设置页更适合聚焦 profile 管理、终端入口和运行环境。
- `WebSocket` 仍保留在顶部摘要中，用来表达“当前 App 与当前 profile 的业务连接是否可用”。

## 四、字体与间距规范

参考 `CronTaskView` 与 `ChannelView`，设置页建议使用本地字号常量，避免散落 `.caption`：

```swift
private enum SettingsFont {
    static let cardTitle: CGFloat = 20
    static let cardSubtitle: CGFloat = 15
    static let body: CGFloat = 16
    static let detail: CGFloat = 15
    static let meta: CGFloat = 14
    static let badge: CGFloat = 13
    static let path: CGFloat = 13
    static let action: CGFloat = 16
}
```

使用规则：

- 页面 Hero 继续复用 `PageHeroHeader`，不改标题 36、副标题 22。
- 卡片标题使用 `.system(size: 20, weight: .semibold)`。
- 主要正文、说明文字、状态说明使用 `.system(size: 16)`。
- 信息行 label 使用 `.system(size: 15)` + `.secondary`。
- 信息行 value 使用 `.system(size: 16, weight: .medium)`，长路径除外。
- 路径使用 `.system(size: 13, design: .monospaced)` 或 `.system(size: 14, design: .monospaced)`，并保留换行与 `textSelection`。
- Badge 使用 13 semibold；只有徽章、极低优先级元信息允许小于 14。
- Button 使用 `.controlSize(.large)` 或 label 内 `.font(.system(size: 16, weight: .semibold))`。

需要替换的典型位置：

- `gatewayActionHint`：从 `.caption` 提升到 15 或 16。
- `terminalSection` 说明：从 `.caption` 提升到 15 或 16。
- `profilesSection` 提示与刷新文案：从 `.caption` 提升到 15。
- `profileInfoRow`：label 15、value 16。
- `profilePathBlock`：title 14、path 13/14 monospaced。
- `ProfileBadge`：从 `.caption` 改为 13 semibold。

## 五、组件拆分方案

优先在 `AppSettingsView.swift` 内新增 private 组件，避免过早扩大公共 API：

### 5.1 `SettingsSectionCard`

职责：

- 统一卡片容器、圆角、背景、描边、padding。
- 支持 title、subtitle、可选固定高度。
- 内部 content 自由组合。
- 操作卡片与系统信息卡片传入固定高度时，要使用 `minHeight == maxHeight`，保证同一组卡片等高。

建议视觉：

```swift
.padding(22)
.background(
    RoundedRectangle(cornerRadius: 24, style: .continuous)
        .fill(Color(nsColor: .controlBackgroundColor))
        .overlay(
            RoundedRectangle(cornerRadius: 24, style: .continuous)
                .stroke(Color.black.opacity(0.08), lineWidth: 1)
        )
        .shadow(color: Color.black.opacity(0.03), radius: 14, y: 6)
)
```

### 5.2 `SettingsInfoRow`

职责：

- 替代 `LabeledContent` 在自绘卡片中的展示。
- label/value 字号可控。
- 长 value 可换行，可选 monospaced。

建议：

- 使用 `Grid` 或 `HStack(alignment: .firstTextBaseline)`。
- label 固定最小宽度 96 或 112，value 撑满。
- 对路径类 value 使用垂直布局，避免横向挤压。

### 5.3 `SettingsStatusPill`

职责：

- 替代 `ProfileBadge` 并可复用于 overview 状态。
- 统一 badge 字号、背景色、圆角和小圆点。

### 5.4 `SettingsOverviewCard`

职责：

- 顶部状态概览小卡。
- 展示 icon、title、value、subtitle，可填满 `LazyVGrid`。

### 5.5 Profile 卡片

现有 `profileCard(for:)` 可保留逻辑，重做视觉：

- 卡片标题：Profile displayName 20 semibold。
- slug：14 monospaced。
- 指标区：端口、配置、PID、最近探测使用紧凑 2x2 指标格，替代长列表信息行。
- legacy profile 的配置指标使用 `可复用 / 缺配置`，避免把“未执行 App 托管 setup”误读为旧配置不可用。
- 错误区：固定高度一行状态提示，正常、未同步、异常都占同样空间。
- 路径区：只保留 `Config` 和 `Workspace`，单行中间截断；点击路径栏打开完整路径 popover，完整内容在 popover 内选中或复制。
- 操作按钮：使用 `.controlSize(.large)`，宽屏单行，窄屏可用 `ViewThatFits` 在 HStack/VStack 之间切换。
- Profile 列表用横向 `ScrollView + LazyHStack`，单张卡片固定宽度与高度，避免多 Profile 时纵向无限增长。

## 六、实现步骤

### Phase 1：页面骨架与容器替换

改动：

- 将 `AppSettingsView.body` 中的 `Form(.grouped)` 替换为 `ScrollView + VStack`。
- 新增 `heroSection`，保持现有 `PageHeroHeader` 文案。
- 新增 `SettingsSectionCard`、`SettingsInfoRow`、`SettingsStatusPill` 等本地 private 组件。
- 先把现有各 Section 内容迁移到卡片，不改业务方法和状态变量。

验收：

- 设置页横向撑满 detail 区域。
- 页面仍可滚动，顶部 Header 与其他页面视觉一致。
- 账户、Profiles、Gateway、终端、环境、关于都还存在。

### Phase 2：字体统一

改动：

- 新增 `SettingsFont` 常量。
- 替换设置页正文级 `.caption`。
- 保留小 badge 与极低优先级元信息的小字号，但不低于 13。
- 为按钮统一 `.controlSize(.large)` 或 16 semibold label。

验收：

- 设置页正文视觉大小接近 `CronTaskView` 和 `ChannelView`。
- 长路径仍能完整阅读，不会被单行截断。
- 中文和英文文案都不显得拥挤。

### Phase 3：Profile 区重做

改动：

- `profilesSection` 改为满宽卡片。
- 移除顶部 Profile Picker，避免和卡片内“切换到此 Profile”重复。
- Profile 列表从 `ForEach` in Form 改为横向 `ScrollView(.horizontal) + LazyHStack`。
- `profileCard(for:)` 重做为大卡片。
- Profile 卡片使用固定宽度与固定高度，降低 Profiles 区域纵向占用。
- Profile runtime 错误统一进入固定高度状态行，避免有错误的卡片变高。
- 长路径只保留紧凑单行展示，完整路径通过 tooltip 查看。
- Profile 操作按钮在窄宽度下自动换行或垂直排列。
- 保留删除确认、导入旧 Profile、刷新运行态、自动恢复 Toggle 的现有行为。

验收：

- 1 个 Profile 时展示为固定宽度卡片，Profiles 区域高度保持紧凑。
- 5 个 Profiles 时展示为一行横向滑动卡片，不出现纵向 `2 + 2 + 1` 排列。
- Profile 状态、错误、路径、操作按钮均可读。
- 删除、启动、停止、重启、准备配置、切换 Profile 行为不变。

### Phase 4：Terminal / System 卡片化

改动：

- 删除设置页内独立的 Gateway 状态/控制卡，避免和其他页面、Profile 卡片内操作重复。
- `toolGrid` 使用固定双列均分布局，Terminal 与 Environment 始终保持同一行并平分整行宽度，不再自动折叠成上下两行。
- Terminal 卡片保留现有 `openWindow(id: "profile-terminal", value: selectedProfile.id.uuidString)` 调用。
- Terminal 卡片显示当前 Profile、slug、工作目录和命令使用说明。
- Terminal 卡片在无 selected Profile / resolution 时展示不可用空态。
- Environment 卡片移动到 `toolGrid`，与 Terminal 保持同排同高，并避免因为列宽上限导致中间留白。
- Account、About 放入 `systemInfoGrid`。
- 顶部 `statusOverviewGrid` 仅保留当前 Profile、WebSocket、环境，不再重复展示 Gateway 状态卡。
- `toolGrid` 与 `systemInfoGrid` 内部卡片维持稳定高度，避免下方卡片有高有矮。

验收：

- 退出登录、重新检查环境、打开内嵌终端都仍可用。
- Gateway 启停操作只在 Profile 卡片中出现，设置页不再出现独立 Gateway 卡。
- 顶部摘要不再重复展示 Gateway 卡，但当前连接状态仍可通过 WebSocket 摘要观察。
- 打开的内嵌终端仍绑定点击时的当前 Profile。

### Phase 5：细节与回归

改动：

- 检查所有新增文案是否使用 `L10n.k` 或复用现有文案。
- 检查 loading、error、empty profile、no selected profile 等状态。
- 确认 `.task`、`.onChange`、`.sheet`、`.confirmationDialog`、`.alert` 保持在外层 view 上。

验收：

- 进入设置页会正常刷新 Profile runtime。
- Profile 变化后仍触发刷新。
- 异常弹窗仍能显示并关闭。
- Sheet 和 confirmation dialog 正常弹出。

## 八、风险与处理

### 8.1 替换 Form 后控件布局需要手动维护

风险：

- `Toggle`、`Button` 在 `Form` 中有系统默认对齐，迁移到卡片后需要手动做 label/value 排版。

处理：

- 对简单键值信息用 `SettingsInfoRow`。
- 对 Toggle 保留原生控件本体，但放在卡片内容区域中。
- 不重写控件交互，只重做容器与文字。

### 8.2 Profile 卡片内容很长

风险：

- Config / Workspace 路径较长，在固定宽 Profile 卡片里可能显得拥挤。
- runtime 错误、长路径、按钮换行都可能把个别卡片撑高，造成同组卡片高低不一。

处理：

- 卡片整体使用固定高度，内容以紧凑指标、单行状态、单行路径组织。
- runtime 错误固定占一行，完整错误放进 `.help()`。
- 路径使用 `~` 缩写和中间截断；默认栏位不启用行内 text selection，避免点击后文字溢出；完整路径通过点击 popover 展示并支持复制。
- Profile 列表改为横向滑动，单张卡片宽度不要低于 420。

### 8.3 横向滑动的发现性

风险：

- macOS 横向滚动对部分用户不够明显，profile 超过当前窗口宽度时可能不知道右侧还有内容。

处理：

- Profiles 区域说明文案明确写出“左右滑动查看更多 Profile”。
- `ScrollView(.horizontal)` 保留 visible scroll indicator。
- 工具栏不放在横向滚动区内，确保新建、导入、刷新始终可见。

### 8.4 当前工作区已有设置页改动

风险：

- `AppSettingsView.swift` 当前工作区已有未提交改动，后续实现时容易覆盖他人修改。

处理：

- 实现前先重新查看 `git diff -- EZRWorkerApp/EZRWorker/Views/Settings/AppSettingsView.swift`。
- 只在当前文件中做 UI 层增量修改，不 revert 既有业务改动。

### 8.5 固定字号与系统可访问性

风险：

- 项目当前主线页面大量使用固定 pt 字号，设置页若完全语义字体可能视觉不一致。

处理：

- 本轮按现有主线视觉使用固定字号，保证页面间一致。
- 不把正文降到 caption；小字号只用于 badge 和 path。

## 十、验收标准

视觉验收：

- 设置页主体不再使用 `Form(.grouped)` 的窄表单视觉。
- 页面内容与其他主线页面一样撑满 detail 区域。
- 正文、说明、信息行字号与 `CronTaskView` / `ChannelView` 接近。
- 除 badge、路径、低优先级元信息外，设置页不再大量使用 `.caption`。
- Profiles 区域保持紧凑高度，多 Profile 通过横向滑动查看。
- 同一组卡片高度一致，下方卡片不再有高有矮。
- 设置页不再出现独立 Gateway 卡片，避免与其他页面信息重复。

功能验收：

- 所有原设置页功能入口都保留。
- Profile 生命周期操作行为不变。
- Gateway 生命周期控制入口统一保留在 Profile 卡片中，设置页不再重复展示独立 Gateway 卡。
- 新增的打开内嵌终端功能保留，并清楚展示当前 Profile 与工作目录。
- Sheet、Alert、ConfirmationDialog 行为不变。
- 环境检查与版本信息仍正常展示。

代码验收：

- 主要改动集中在 `AppSettingsView.swift`。
- 不修改 Profile/Gateway/Supervisor 数据模型。
- 不引入新的网络请求或后台任务。
- 构建通过，且不产生明显 SwiftUI 类型推断过慢问题。

## 十一、推荐落地顺序

1. 先做 Phase 1 + Phase 2，解决“没撑满”和“文字太小”的核心问题。
2. 再做 Phase 3，重点优化 Profile 卡片，因为这是设置页内容最多的区域。
3. 最后做 Phase 4 + Phase 5，补齐 overview、边界状态和视觉细节。

这样可以先快速拿到可验证的视觉改观，同时把业务逻辑风险控制在最低。
